# skyward-common v1.6.2

Released 2026-10-09. ClickUp 86bcg2ebk.

One new DataForSEO endpoint: ChatGPT fan-out queries. Nothing existing changes behaviour,
so upgrading needs no code changes.

## What fan-out is

When ChatGPT answers a question with web search, it runs one or more searches of its own.
Those search strings are the fan-out queries. They show which angles a page has to cover to
be found and cited by the answer.

## The call

```python
from skyward.data.dataforseo import DataForSEOClient, fanout_prompt_id
from skyward.functions import generate_job_id

ep = client.ai_optimization_chat_gpt_llm_scraper

# Bulk: the queue. $0.0012 a prompt, 100 prompts per request.
df = await ep.post_all(prompts, job_id=generate_job_id())

# Small and immediate: live. $0.004 a prompt.
df = await ep.live_all(prompts[:5], job_id=generate_job_id())

# Price it first. Spends nothing.
ep.estimate_cost(prompts, endpoint_mode="standard").max_usd
```

It wraps DataForSEO AI Optimization, ChatGPT LLM Scraper
(`v3/ai_optimization/chat_gpt/llm_scraper`). DataForSEO drives the real ChatGPT web UI, so
there is no model to choose; the model that answered is in the `model` column.

## Settings

| Setting | Default | What it does |
|---|---|---|
| `force_web_search` | `True` | Makes ChatGPT search |
| `samples` | `1` | Runs per prompt |
| `retry_empty` | `1` | Resubmits an empty run |
| `priority` | `1` | `2` = faster queue, double price |
| `store_answer` | `True` | Keep the answer text |
| `use_collector` | config | Cloud collector drains results |
| `max_workers` | `10` | Live mode only, capped at 25 |

Plus the usual `upload`, `balance_buffer`, `ignore_balance_check`,
`ignore_location_check` and `upload_batch_rows`.

## Things to know before using it

**Force web search, or expect gaps.** In testing, forced runs returned fan-out 207 times
out of 207. Unforced runs came back empty about a quarter of the time, always for the same
kind of prompt: evergreen questions the model answers from memory. Retrying an unforced
empty the same way does not help, so a retry always forces the search.

**Fan-out is a sample, not a fixed set.** A run returns 1 to 5 queries. Running the same
prompt again rewords them and occasionally adds another angle; ten runs of one prompt gave
ten wordings of mostly the same intent. There is no number of runs at which it settles.
Use `samples=N` when you want more angles, and read the `_queries` view, which unions
every run of a prompt and says how often each query showed up.

**Location is country level only.** The scraper accepts 191 countries and nothing finer.
A prompt with no place in it gets a random city of that country in its fan-out, a
different one each run ("charter bus rental" produced Dallas, Detroit, Tampa, Las Vegas
and more). To get local fan-out, put the place in the prompt. A city or state
`location_code` raises `InvalidLocationError` before anything is sent.

**No domain.** The same prompt can serve several clients, so this endpoint takes no
`domain` or `domain_id` (passing one raises `TypeError`) and the two domain columns in the
table are always NULL. Rows are keyed by `prompt_id`:
`fanout_prompt_id(text)` is the first 16 hex characters of SHA-256 over the prompt after
Unicode NFC normalisation and a strip of the ends. Case and inner whitespace are kept.
Link prompts to clients with your own prompt-to-client table on `prompt_id`.

**Prompts are cleaned, checked and de-duplicated first.** Empty prompts and prompts over
2,000 characters are not sent; they are listed in `ep.rejected_prompts` and still get a
row. Duplicates within a call are collapsed. `%` and `+` are escaped on the way out,
because DataForSEO otherwise turns `+` into a space.

**Every task gets a row.** Failed, refused and empty tasks are written too, with
`status_code` and `status_message`. `fan_out_count` is NULL, not 0, when ChatGPT did not
search.

## Scale

Queue mode sends 100 prompts per request, so 5,000 prompts is 50 requests. Results are
collected as they become ready and saved every 200 rows, so a crash loses little. In
testing, 300 prompts were all back within five minutes.

If the queue does not finish inside `config.task_total_timeout`, everything collected is
kept and `IncompleteTaskError` carries the outstanding `task_ids` (and `.prompts`). Fetch
them later, at no cost, with `ep.collect(task_ids, job_id=...)`; DataForSEO keeps results
for 30 days.

Live mode is one prompt per request. Each call waits up to 180 seconds and is never sent
again after a timeout, since it may already have been billed; that prompt gets a row
saying "possibly billed". Use it for small pulls.

## Collector mode

`use_collector=True` submits, records tracking rows and returns the usual receipt; the
collector VM drains results into the table.

- **The collector VM must be running v1.6.2 first.** An older collector does not know this
  endpoint, so the tasks would never be drained and the call would wait until it times out.
- `retry_empty` is not available here (the collector cannot resubmit) and defaults to 0;
  passing a positive value raises `ValueError`.
- Prompts refused locally are returned in the receipt under `rejected_prompts`.

## The table

`data-hub-468216.DataForSEO.ai_optimization-chat_gpt-llm_scraper`, partitioned by day of
`ingest_timestamp`, clustered by `prompt_id, job_id`. One row per task.

Standard metadata: `job_id`, `upload_id`, `ingest_timestamp`, `domain_id` (NULL),
`domain` (NULL), `task_id`, `endpoint_mode`.

| Column | Meaning |
|---|---|
| `prompt_id`, `prompt` | Join key and text |
| `location_code`, `language_code` | What was sent |
| `force_web_search` | Flag sent for this task |
| `attempt` | 1..samples, then retries |
| `status_code`, `status_message` | Outcome |
| `model`, `answered_at` | What answered, when |
| `fan_out_count` | NULL if none |
| `source_count` and other counts | For filtering |
| `answer_chars`, `answer_markdown` | The answer |

Lists are JSON text, like every other DataForSEO table:

| Column | Each element |
|---|---|
| `fan_out_queries` | string |
| `sources` | position, url, domain, title, source_name, publication_date, citation_count |
| `search_results` | position, url, domain, title |
| `brand_entities` | name, description, category |
| `local_businesses` | title, domain, url, address, phone, rating, reviews_count |
| `item_types` | string |

```sql
-- Every distinct fan-out query for one prompt, and how often it appeared
SELECT query, runs_with_query, runs_total
FROM `data-hub-468216.DataForSEO.ai_optimization-chat_gpt-llm_scraper_queries`
WHERE prompt_id = @prompt_id
ORDER BY runs_with_query DESC;
```

## Operations (one time, in this order)

1. `python scripts/create_dfs_fanout_table.py --yes` creates the table and both views.
2. `python scripts/create_dfs_cost_tables.py --yes` adds the `in_llm_scraper` column to
   `DataForSEO.locations` (the rest of that script is a no-op on existing objects), then
   `python scripts/refresh_dfs_locations.py` fills it.
3. `python scripts/seed_dfs_cost_estimates.py --yes` pushes the two new rates.
4. Redeploy the collector VM with v1.6.2 before using collector mode.

Each script prints what it would do when run without `--yes`.

## Other changes

- `DataForSEOClient._post` takes `timeout=` (default 30, unchanged).
- A run whose endpoint has no rate now prints a warning that the balance guard is off.
- The location catalog treats a flag column that is missing or never filled as "unknown"
  and does not block on it, so the three existing flags keep working before step 2 runs.
