# skyward-common v1.7.0

Additive. No existing call changes behaviour.

## Why

The operator dashboard reads Supabase only, so it could not see when a
warehouse feed last had data. It judged BusBank's Search Console from a stale
copy in its own repo and called a healthy feed "broken" (ClickUp 86bd62xvt,
pipeline.request 61cb057d). This release gives the pipeline a place to write
the real date and the dashboard a place to read it.

## Added

- **Migration `meta_029_dataset_last_day`.** Two columns on
  `meta.dataset_catalog`:
  - `last_day` (date): the latest day the dataset held.
  - `last_day_checked_at` (timestamptz): when that was read.

  Three states: no check time means nobody has looked; a check time with no
  day means we looked and found nothing to date; both set is the reading. A
  check constraint stops a day being stored without a check time. Also
  grants `dashboard_ro` select on the catalogue.
- **`MetaClient.record_dataset_last_days(rows)`.** One batched `UPDATE` for
  many datasets. Refuses a row with no dataset or no check time, so a failed
  read can never overwrite a good date with a null.
- `get_dataset_catalog()` now returns `last_day` and `last_day_checked_at`.

## Reading it

Join `meta.data_access.dataset_id` to `meta.dataset_catalog.dataset`. The
date lives on the dataset, not the access row, because one Search Console
dataset can serve more than one site.

Whether a feed is "broken" is the reader's call: compare `last_day` with the
source's normal lag (Search Console runs about 2-3 days behind, GA4 and Ads
about 1), and only when `last_day_checked_at` is recent.

## Applying

Apply `db/supabase/migrations/20261124120000_meta_029_dataset_last_day.sql`
as `postgres`. Nothing writes the columns until the pipeline's daily check
ships.
