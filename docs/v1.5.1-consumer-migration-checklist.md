# skyward-common v1.5.1 — Consumer Migration Checklist

This release contains a **breaking change to the LLM provider interface**, a cost-accuracy fix, an additive competitor data model, and the DataForSEO standard-mode work. Every repo that imports `skyward.llm` must read **Section 1** before bumping. Sections 2–5 are additive/optional.

**Affected repos (known LLM consumers):** `skyward-seo-pipeline-kagg` (categorize + `llm_log`), AI-Content-Workflow / FAQs, WQA GA4 loader, `reddit-monitor`, and anything else calling `provider.call(...)`.

---

## 1. LLM provider — `provider.call()` now returns `LLMResult` (BREAKING)

### What changed
`provider.call(...)` (all 5 providers: OpenAI, Gemini, Perplexity, Anthropic, Grok) **no longer returns a `(content, input_tokens, output_tokens)` tuple.** It returns a single `LLMResult` dataclass. `call_text()` / `call_structured()` return `LLMResult` too.

```python
@dataclass
class LLMResult:
    content: Any                  # parsed model (if response_model) OR full text
    input_tokens: int
    output_tokens: int
    cache_read_tokens: int = 0
    cache_write_tokens: int = 0
    latency_ms: int | None = None
    model: str | None = None
    stop_reason: str | None = None
    raw_text: str | None = None        # provider text pre-parse
    reasoning_text: str | None = None  # gpt-5*/o1*/Gemini-thinking/Claude-thinking; else None
    raw: Any = None                    # untouched SDK response
```

### Required code changes
Find every call site that unpacks the 3-tuple and update it:

```python
# BEFORE
result, in_tok, out_tok = provider.call(messages, model, response_model=Foo)

# AFTER
r = provider.call(messages, model, response_model=Foo)
result  = r.content
in_tok  = r.input_tokens
out_tok = r.output_tokens
```

- [ ] Grep each repo for `.call(`, `.call_text(`, `.call_structured(` and any tuple-unpack of the result.
- [ ] Replace tuple unpacking with `.content` / `.input_tokens` / `.output_tokens`.
- [ ] **`LLMSession.send()` is UNCHANGED** — it still returns the content (string or parsed model), not an `LLMResult`. Session token totals (`session.total_input_tokens` / `total_output_tokens`) still work.

### New capabilities you can now use (optional)
- [ ] `r.cache_read_tokens` / `r.cache_write_tokens` — prompt-cache usage (see Section 2 for cost).
- [ ] `r.latency_ms` — per-call latency.
- [ ] `r.raw_text` — provider text before parsing (useful for `llm_log` audit).
- [ ] `r.reasoning_text` — reasoning/thinking summary for reasoning models (OpenAI gpt-5*/o1* require requesting a summary, e.g. `reasoning={"summary": "auto"}`; Anthropic populates it when extended thinking is enabled; `None` otherwise).
- [ ] `r.stop_reason`, `r.model`, `r.raw`.

### kagg `llm_log` specific
- [ ] Wire the placeholder columns to the new fields: `output_raw_text ← r.raw_text`, `reasoning_text ← r.reasoning_text`, and store `cache_read_tokens` / `cache_write_tokens` / `latency_ms`.
- [ ] Update the categorize stage's tuple-unpack (Section 1) and the pre-run estimate.

## 2. `calculate_cost()` — corrected rates + cache-aware (action: re-baseline cost numbers)

### What changed
- **gpt-5 family rates were wrong** (gpt-5-mini billed at gpt-4o-mini rates → ~3× undercount). Now correct: gpt-5 `1.25/10`, gpt-5-mini `0.25/2.00`, gpt-5-nano `0.05/0.40`. Verified vs live OpenAI pricing (Jun 2026).
- **Date-suffixed model ids are matched to the family** (`gpt-5-mini-2025-08-07` → `gpt-5-mini`).
- **Cache-aware:** new optional kwargs `cache_read_tokens=` / `cache_write_tokens=`. Per-model cached rates (gpt-5 fam = 10% of input, gpt-4o fam = 50%, Anthropic read = 10%, 5m write = 1.25×). For OpenAI/Gemini, `input_tokens` is assumed to **include** cached tokens (cache reads are subtracted before billing); for Anthropic they are separate.
- **Anthropic cost table refreshed** to current models (`claude-opus-4-8`, `claude-sonnet-4-6`, `claude-haiku-4-5-20251001`); retired keys kept for historical rows.

### Required / recommended
- [ ] **Expect cost numbers to change.** Any consumer reporting "actual cost" for gpt-5* will now report the correct (higher) value. Re-baseline dashboards/budgets/alerts.
- [ ] Pass cache tokens for accurate cost: `calculate_cost(r.input_tokens, r.output_tokens, model, provider, cache_read_tokens=r.cache_read_tokens, cache_write_tokens=r.cache_write_tokens)`.
- [ ] Signature is backward-compatible (new args default to 0) — existing positional calls keep working, just more accurate.
- [ ] (Optional) historical `llm_log.cost_usd` rows under-bill gpt-5*; backfill if you need accurate history.
- [ ] ⚠️ **Gemini cost table was NOT updated** this release (tiered pricing) — treat Gemini cost as approximate until a follow-up.

## 4. Site-scoped competitors (ADDITIVE — non-breaking; migrate when ready)

No code breaks here. New `meta.site_competitors` table + MetaClient/DataHub helpers model competitors **per site** (directional). The legacy `client_domains.is_competitor` flag is **untouched and still authoritative** until you migrate consumers.

- Prod is already backfilled (client-level competitors fanned out to each client's brand sites; multi-site fan-outs are a "safe superset" pending manual trim).
- New helpers: `get_site_competitors`, `add_site_competitor`, `add_site_competitors`, `add_site_competitor_by_domain`, `get_sites_competing_with`, `remove_site_competitor`, `set_site_competitor_priority`, `set_site_competitors`, `copy_site_competitors`, `get_client_competitors`, `set_client_domain_competitor`.
- [ ] (Later) KAGG competitor resolution (`shared.competitors.domain_ids`, `load_competitors`) → read from `site_competitors` / `get_client_competitors`.
- [ ] (Later) `seo_pipeline` `_lookup_client_id` → unchanged (still uses ownership = `is_competitor=false`).

## 5. DataForSEO — standard-mode collector + debug logging (ADDITIVE — both opt-in, off by default)

Two independent DFS additions. **Nothing changes unless you opt in.** 5a changes `post_all`'s return type *only when you enable collector mode*; 5b is pure opt-in instrumentation.

### 5a. Standard-mode collector — submit & walk away (opt-in)

**What changed.** The standard-mode (`task_post` → poll → `task_get`) endpoints — `serp_google_organic` and `keywords_data_google_ads_search_volume` — can now **submit tasks and exit** instead of polling in-process for up to hours. An always-on collector service (running on a VM) drains DFS independently and writes results straight to the canonical BigQuery tables. This kills the old in-process failure mode (a stuck run hanging for hours and losing every row on crash/Ctrl-C).

**Default is unchanged.** With the flag off (default), `post_all()` keeps the legacy in-process behavior and return type:
- `serp_google_organic.post_all(...)` → `(results_df, failed_df)`
- `keywords_data_google_ads_search_volume.post_all(...)` → `DataFrame`

**⚠️ When you enable collector mode, `post_all()` returns a receipt dict, NOT a DataFrame.** Any code that unpacks `(df, failed_df)` (or uses the returned frame) will break if you flip the flag — read results from BigQuery instead (below). This is the one thing to watch when opting in, especially via the global toggle.

**Enable it — global toggle or per-call:**
```python
from skyward.data.dataforseo import ClientConfig, DataForSEOClient

# Global (applies to every post_all on this client)
client = DataForSEOClient(username=..., password=..., bq_client=bq,
                          config=ClientConfig(use_collector=True))

# …or per call (overrides config)
receipt = await client.serp_google_organic.post_all(
    targets=keywords,            # list[str]
    job_id=job_id,               # your run id (required)
    domain_id=43,                # attribution → stamped on the canonical rows
    use_collector=True,          # per-call override
    proceed_at_pct=0.95,         # return once 95% of tasks have results (default 1.0)
    location_code=2840, language_code="en",   # serp; search_volume uses language_name="English"
)
```

**`proceed_at_pct`** controls how long the producer waits before returning: `1.0` (default) waits for all tasks, `0.0` is pure fire-and-exit. Stragglers keep landing in BigQuery regardless — the collector owns the tail.

**The receipt dict:**
```python
{ "job_id": "...", "endpoint": "serp_google_organic",
  "total_tasks": 5000, "completion_pct": 0.95, "proceeded": True,
  "rejected_payment": 0,   # 40200 (balance) rejects detected at submit
  "rejected_other": 0 }
```

**How to read your results** (data lands in BQ as the collector drains, tagged with your `job_id` + `endpoint_mode='standard'`):
```python
# Option A — direct query
#   serp:          data-hub-468216.DataForSEO.serp-google-organic
#   search_volume: data-hub-468216.DataForSEO.keywords_data-google_ads-search_volume
SELECT * FROM `data-hub-468216.DataForSEO.serp-google-organic`
WHERE job_id = @job_id AND endpoint_mode = 'standard'

# Option B — DataHub helper (resolves the client's domains via Supabase Meta)
df = hub.get_client_data(client_id="123", dataset="DataForSEO",
                         table="serp-google-organic", use_domain_lookup=True)
```

**Checklist (only if you opt in):**
- [ ] Decide global (`ClientConfig(use_collector=True)`) vs per-call (`use_collector=True`). Prefer per-call first.
- [ ] Replace any `(df, failed_df)` / DataFrame handling of `post_all`'s return with **receipt-dict handling + a BigQuery read** of the canonical table by `job_id`.
- [ ] Always pass `domain_id` (or `domain`) so rows are attributed (else they land under the `d4s_standard_unattributed` sentinel with no domain).
- [ ] Set `proceed_at_pct` to taste (e.g. `0.0` to fire-and-exit, `0.95` to mostly-wait).
- [ ] One-time per project: ensure the tracking tables exist — `python scripts/create_dfs_collector_tables.py --yes` (creates `DataForSEO.dfs_job_summary` + `DataForSEO.dfs_task_log`). The collector service must be running for results to land.
- [ ] (Optional) monitor progress: `TrackingStore(bq).job_status(job_id=..., endpoint=...)` → `{total_tasks, fetched, failed, status, completion_pct}`, or query `DataForSEO.dfs_job_summary`.

### 5b. Per-attempt debug logging — `include_debug_logs` (opt-in)

**What changed.** `live()` / `live_all()` accept a new `include_debug_logs: bool = False`. When `True`, every API attempt (including retries) is logged to a shared BigQuery table — request payload, full response, timing, DFS task status, retry attempt #, etc. Zero overhead when off.

```python
df = await client.dataforseo_labs_google_keyword_suggestions.live_all(
    targets=seeds, domain="busbank.com", job_id=job_id,
    include_debug_logs=True,    # ← writes per-attempt rows to DataForSEO.debug_request_logs
)
```

- **Table:** `data-hub-468216.DataForSEO.debug_request_logs` (one row per attempt: `job_id, upload_id, endpoint, target, attempt, is_terminal, started_at, duration_ms, http_status, task_status_code, task_status_message, task_cost, n_items, payload, response, error, ingest_timestamp`). One-time: `python scripts/create_dfs_debug_log_table.py --yes`.
- **Coverage today:** capture is wired on `keyword_suggestions` and `related_keywords` (the endpoints from the empty-payload investigation). Other endpoints accept the flag but don't emit yet (TODO) — so passing it elsewhere is a harmless no-op for now.
- **Sizing:** each row's `response` is ~5–15 KB; a ~14K-call run ≈ ~100 MB. Use it for **debugging** (e.g. diagnosing empty post-get / retry behavior), not as always-on logging. Credentials are never logged (auth lives outside the payload).
- [ ] Use `include_debug_logs=True` only for investigations; leave it off (default) in steady state.

### 5c. Prerequisite (since v1.5.0): domain resolution is via Supabase Meta

Any DFS call passing `domain=` or `domain_id=` (including collector attribution above) resolves the domain through **Supabase `meta.domains`**, not BigQuery — so `SUPABASE_DB_URL` must be set. This shipped in v1.5.0 (see `MIGRATION_v1.5.0.md`); opt out per-call with `domain=None`.
