# skyward-common v1.6.1 — DataForSEO cost tracking

## What changed for consumers

Nothing is required. Upgrading gives you automatic DataForSEO cost logging, estimates,
progress and periodic saves. Two new errors can now be raised before (or during) a run;
handle them if your pipeline should react.

## New behavior

- **Cost log.** Every billed DataForSEO task is written to `DataForSEO.cost_log`, tied to
  your `job_id`, the `upload_id` of the save window its rows landed in, and the DFS
  `task_id`. Look up spend with `client.get_job_cost(job_id)`.
- **Estimates.** `client.<endpoint>.estimate_cost(targets, **kwargs)` returns a worst-case
  `max_usd` (list price + 10%) and an `avg_usd` from observed actuals.
- **Progress.** `client.get_job_progress(job_id)` shows status and percent complete per
  endpoint, readable from another thread or process while the job runs.
- **Periodic saves.** Large runs save to BigQuery every 10k rows (up to 100k expected rows)
  or every 50k rows (above that). A crash loses at most one window. Override with
  `upload_batch_rows=`. The DataFrame returned is unchanged.
- **Locations.** `client.get_locations(...)` reads a cached catalog of every DFS location
  code, with flags for which endpoint families accept it.
- **Search volume language.** `keywords_data_google_ads_search_volume` (and
  `ranked_keywords`) now send `language_code` instead of always sending English.

## New errors

### `InsufficientBalanceError`

Raised when the DataForSEO balance is below the run's max estimate x `balance_buffer`
(default 1.2).

- Before a run starts: nothing was spent. Top up, lower the scope, or pass
  `ignore_balance_check=True` to run anyway (a warning is printed).
- During a run (re-checked at every data save): everything fetched so far has been saved.
  The error carries `job_id`, `endpoint`, `upload_ids`, `completed_targets` and
  `remaining_targets`. skyward-common does **not** skip data already pulled, so a rerun
  with the same inputs pulls everything again. To resume, rerun only
  `remaining_targets`, or rely on your pipeline's own "already have this" check.

### `InvalidLocationError`

Raised before a run when `location_code` isn't accepted by the endpoint family (for
example a DMA code on a Labs endpoint, which only accepts countries). Nothing was spent.
Pass `ignore_location_check=True` to send it anyway. The check is skipped when the
location catalog hasn't been loaded.

## New optional parameters (every `live`, `live_all`, `post`, `post_all`)

| Parameter | Default | Meaning |
| --- | --- | --- |
| `balance_buffer` | `1.2` | Multiplier on the max estimate for the balance check |
| `ignore_balance_check` | `False` | Run even when balance is too low (prints a warning) |
| `ignore_location_check` | `False` | Send a location code the catalog says is unsupported |
| `upload_batch_rows` | `None` | Rows per save window (None = sized automatically) |

## Known limits

- **`backlinks_bulk_pages_summary` cost estimate does not cover the invalid-URL retry
  path.** When a batch sent to this endpoint contains a target DataForSEO rejects as an
  unparseable invalid URL, the client recursively splits that batch in half (up to 5
  levels) to isolate and skip the bad target, and each split re-sends the remaining
  targets as its own billed request. A batch made entirely of clean, well-formed URLs is
  unaffected and costs exactly what `estimate_cost` says. A batch that includes URLs
  DataForSEO can't parse (not just backlinks it has no data for — actually malformed
  target strings) can cost several times its estimate, since every extra split is a real
  DataForSEO charge that happened outside the plan. If you're feeding this endpoint
  user-supplied or scraped URLs, filter out anything that isn't a well-formed URL before
  calling it.

- **Two endpoints' worst-case defaults need a bigger account balance than their typical
  cost.** The balance guard always sizes itself against the worst case a run *could* hit,
  not what it's likely to hit, so a small account can get rejected on runs that would
  actually have been cheap. Two endpoints have unusually large worst cases relative to
  their normal use:
  - `ranked_keywords.live_all(...)` — with the default `limit_per_domain=10000` (pulled
    1,000 keywords per page), the worst case is about **$1.32 per domain**, because the
    estimate has to assume every domain actually has 10,000 ranked keywords to page
    through, even though most domains have far fewer.
  - `backlinks_backlinks` — with `limit=None` (the default), the worst case is about
    **$1.20 per target**, because the estimate has to assume DataForSEO's 20,000-row
    offset ceiling is fully used, even though most targets have far fewer backlinks.
  With `balance_buffer=1.2` (the default), a plain `ranked_keywords.live_all(...)` call
  over roughly 18+ domains can raise `InsufficientBalanceError` on an account with only
  ~$30 in it, even though the run's *actual* cost would have been a small fraction of
  that. If this happens and you know your real usage is much lower than the worst case,
  either pass a smaller `limit`/`limit_per_domain` (which shrinks the worst case itself,
  not just the estimate), or pass `ignore_balance_check=True` to proceed anyway.

- **`cost_log` is best-effort attribution, not a billing ledger.** It records the cost of
  a billed DataForSEO request only when a well-formed response for that request actually
  comes back and gets parsed. A request DataForSEO billed but whose response never
  arrives intact (a 5xx, a dropped connection, unparseable JSON) is not logged, and
  neither is a request the client's own session-level `Retry` retried for a 429 or 5xx
  before it succeeded — only the response that logging code actually sees is recorded.
  Treat `cost_log` as a diagnostic breakdown of spend by job/endpoint, not as the total;
  your DataForSEO account balance remains the source of truth for what you were actually
  charged.

## Not in this release

- Returning a run summary instead of the DataFrame (bounded memory on huge pulls) — its own
  task, because it changes return types.
- LLM provider cost tracking — planned for a later update of v1.6.1.
